# Практикум: свой MCP-сервер для Claude Code и Claude Desktop

Цель — своими руками написать простейший локальный MCP-сервер «Заметки» на Python, проверить его в MCP Inspector, а затем подключить к Claude Code и Claude Desktop и посмотреть, как Claude с ним работает.

- **Без API-ключей и без собственного клиента**: во время разработки сервер проверяется в MCP Inspector, а в последнем модуле клиентами выступают Claude Code и Claude Desktop.
- **Без хостинга**: сервер работает локально через stdio, клиент сам запускает его как подпроцесс.
- **Без готовых решений**: в каждом шаге есть задание, подсказки по API и критерий проверки. Код пишете вы.

Версия SDK: `mcp` **2.3.0** (PyPI, октябрь 2026).
> ⚠️ В SDK v2 класс `FastMCP` переименован в `MCPServer`. Большинство туториалов в интернете (и курс в `cli_project`) написаны под v1: `from mcp.server.fastmcp import FastMCP`. В v2 этот импорт падает с `ModuleNotFoundError`. Если пример из интернета не работает, сначала проверьте версию.

### Документация 
- MCP Python SDK: https://py.sdk.modelcontextprotocol.io
- Claude Code MCP: https://code.claude.com/docs/en/mcp
- Claude Desktop и локальные MCP-серверы: https://modelcontextprotocol.io/docs/develop/connect-local-servers

## Как устроен сервер «Заметки»

```
mcp_practice/
├── COURSE.ru.md     ← этот файл
├── server.py        ← ваш MCP-сервер
└── notes/           ← «база данных»: обычные .md файлы
    ├── shopping.md
    └── ideas.md
```

К концу курса сервер будет уметь:

| Возможность | Что это | Кто инициирует |
|---|---|---|
| **Tools** `list_notes`, `read_note`, `write_note` | Действия | Claude решает сам, когда их вызвать |
| **Resources** `notes://index`, `notes://{name}` | Данные для чтения | Вы, прикрепив ресурс к сообщению |
| **Prompts** `summarize_note` | Готовые шаблоны запросов | Вы, выбрав промпт в меню клиента или слэш-командой |

## Модуль 1. Скелет сервера

### Шаг 1.1 — Минимальный сервер
- [ ] Создать `server.py`: экземпляр сервера с именем `"Notes"` и запуск по stdio, когда файл выполняется как скрипт.

**Документация:** [First steps](https://py.sdk.modelcontextprotocol.io/get-started/first-steps/), [Connect to a real host](https://py.sdk.modelcontextprotocol.io/get-started/real-host/)

**Подсказка:**
- Сохраните экземпляр в переменную уровня модуля с именем `mcp`: `mcp = MCPServer("Notes")`. Дальше в курсе все подсказки используют это имя (`@mcp.tool()`, `@mcp.resource()`, `@mcp.prompt()`), а команды `mcp dev` и `mcp run` ищут в файле объект с именем `mcp`, `server` или `app`.

### Шаг 1.2 — Эксперимент: побыть клиентом самому
- [ ] Запустить `uv run server.py` и вставить в терминал три сообщения по очереди, нажимая Enter после каждого. Каждое сообщение — одна строка JSON.

1. `initialize`:
   ```json
   {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"manual","version":"0.1"}}}
   ```
2. `notifications/initialized`:
   ```json
   {"jsonrpc":"2.0","method":"notifications/initialized"}
   ```
3. `tools/list`:
   ```json
   {"jsonrpc":"2.0","id":2,"method":"tools/list"}
   ```

**Что увидите:**
- После `initialize` сервер ответит строкой, в которой есть `"serverInfo":{"name":"Notes",...}` и список его возможностей.
- На `notifications/initialized` ответа не будет: это уведомление, у него нет `id`.
- `tools/list` вернёт `{"tools":[]}`: инструментов пока нет.

Остановите процесс через `Ctrl+C`.

**Что заметить:**
- `initialize` обязательно идёт первым: это рукопожатие, в котором клиент и сервер договариваются о версии протокола.
- Поле `id` связывает ответ с запросом.
- Ровно этот обмен за вас выполняют MCP Inspector и клиенты вроде Claude Code и Claude Desktop. Повторите `tools/list` после модуля 2 и увидите `list_notes` с описанием и схемой аргументов.

## Модуль 2. Первый инструмент (tool)

### Шаг 2.1 — `list_notes`
- [ ] Написать инструмент `list_notes`, который возвращает отсортированный список имён файлов из папки `notes/`.

**Документация:** [Tools](https://py.sdk.modelcontextprotocol.io/servers/tools/), [Structured Output](https://py.sdk.modelcontextprotocol.io/servers/structured-output/)

**Подсказки:**
- Инструменты пишите прямо в `server.py`. Функцию из другого файла недостаточно импортировать: её нужно ещё зарегистрировать на сервере. Как это сделать, описано в разделе [«Инструменты в отдельном файле»](#инструменты-в-отдельном-файле) в конце курса.
- Запуск сервера (блок `if __name__ == "__main__":`) должен оставаться в конце файла: `mcp.run()` не возвращает управление, и всё, что ниже, не выполнится. В Inspector такая ошибка незаметна, потому что `mcp dev` импортирует файл и этот блок не выполняет.
- Docstring — строка в тройных кавычках сразу под `def`. Это не просто комментарий: SDK отправляет её модели как описание инструмента, и по нему модель решает, когда инструмент вызывать. Без docstring модель видит только имя функции и её аргументы. Для `list_notes` подойдёт, например:
  ```python
  """List the names of all notes (Markdown files) in the notes folder."""
  ```
- Путь к папке стройте от расположения файла, а не от текущей директории: `Path(__file__).parent / "notes"`. Клиент может запустить сервер из другой рабочей папки.
- Тип возврата: `list[str]` или `str`. Попробуйте оба варианта и посмотрите в Inspector, чем отличается результат.

### Шаг 2.2 — Проверка в MCP Inspector
- [ ] Запустить `uv run mcp dev server.py`.
- [ ] В открывшемся браузере нажать Connect → вкладка **Tools** → `list_notes` → Run.

**Документация:** [First steps](https://py.sdk.modelcontextprotocol.io/get-started/first-steps/) (раздел про `mcp dev`)

**Проверка:** видите список своих файлов.

**Зачем этот шаг:** Inspector — тоже MCP-клиент, только ручной. Так вы отлаживаете сервер без участия модели и видите сырой JSON запросов и ответов.

**Примечание:** изменения в `server.py` Inspector сам не подхватывает. Чтобы он увидел новый код, нажмите в нём Disconnect, а затем Connect: Inspector запустит сервер заново. Перезапускать `mcp dev` не нужно.

## Модуль 3. Чтение заметки и обработка ошибок

### Шаг 3.1 — `read_note(name)`
- [ ] Инструмент принимает имя заметки и возвращает её текст.

**Документация:** [Tools](https://py.sdk.modelcontextprotocol.io/servers/tools/)

**Подсказка:** в docstring укажите то, чего не понять из имени: в каком формате ожидается `name` (например, имя файла с расширением `.md`, как его возвращает `list_notes`).

### Шаг 3.2 — Ожидаемые ошибки
- [ ] Если заметки нет, вернуть понятную модели ошибку, а не падать с трейсбеком.

**Документация:** [Handling errors](https://py.sdk.modelcontextprotocol.io/servers/handling-errors/)

### Шаг 3.3 — Безопасность путей
- [ ] Запретить чтение за пределами `notes/`.

**Почему это нужно.** Сейчас `read_note` склеивает путь как `NOTES_DIR / name` и читает любой файл, до которого дотянется. Опасных случаев два:
- `name="../pyproject.toml"`: `..` выводит из папки `notes/` наверх.
- `name="C:/Windows/win.ini"` (на macOS и Linux — `name="/etc/hosts"`): если справа от `/` стоит абсолютный путь, `pathlib` отбрасывает всё, что слева, и `NOTES_DIR` просто исчезает.

**Подсказки:**
1. Приведите путь к окончательному виду: `(NOTES_DIR / name).resolve()`. [`resolve()`](https://docs.python.org/3/library/pathlib.html#pathlib.Path.resolve) делает путь абсолютным и убирает `..`: `notes/../pyproject.toml` превращается в `.../mcp_practice/pyproject.toml`.
2. Проверьте, что результат лежит внутри папки заметок: [`path.is_relative_to(NOTES_DIR.resolve())`](https://docs.python.org/3/library/pathlib.html#pathlib.PurePath.is_relative_to). Папку тоже приведите через `resolve()`, иначе сравнятся пути разного вида.
3. Если проверка не прошла, бросьте `ToolError`, как в шаге 3.2.
4. Эта проверка понадобится ещё в `write_note` (шаг 4.1) и в ресурсе `notes://{name}` (шаг 6.2), поэтому удобно вынести её в отдельную функцию.

### Шаг 3.4 — Проверка в Inspector
- [ ] Вызвать `read_note` с именем существующей заметки, например `shopping-list.md`.
- [ ] Вызвать `read_note` с именем несуществующей заметки.
- [ ] Вызвать `read_note` с `name="../pyproject.toml"` и с `name="C:/Windows/win.ini"` (на macOS и Linux — `name="/etc/hosts"`).

**Проверка:**
- существующая заметка возвращает свой текст;
- для несуществующей заметки Inspector показывает ошибку с вашим текстом;
- оба опасных пути возвращают ошибку, а не содержимое файла.

**Эксперимент:** временно замените `ToolError` на обычный `ValueError` и снова вызовите `read_note` с несуществующей заметкой. Вашего текста больше не видно, есть только общее «Error executing tool read_note»: сообщения непредвиденных исключений SDK клиенту не передаёт. После эксперимента верните `ToolError`.

Как на такую ошибку реагирует модель, вы увидите в модуле 8.

**Вопрос для понимания 2.** Почему проверку путей нужно делать в сервере, а не надеяться, что модель не попросит лишнего? ([ответ](#ответы-на-вопросы-для-понимания))

**Дополнительно:** пометьте свои инструменты аннотациями. Документация: [Names, titles, and annotations](https://py.sdk.modelcontextprotocol.io/servers/tools/#names-titles-and-annotations).

| Аннотация | Вопрос, на который отвечает | Для каких инструментов |
|---|---|---|
| `read_only_hint` | Инструмент ничего не меняет? | для читающих |
| `destructive_hint` | Может ли он удалить или затереть существующие данные? | только для изменяющих |
| `idempotent_hint` | Повторный вызов с теми же аргументами безопасен, результат тот же? | только для изменяющих |
| `open_world_hint` | Работает ли он с внешним миром (интернет), а не с закрытым набором данных? | для любых |

Каждая аннотация принимает только `True` или `False`.

## Модуль 5. Логирование

**Главное:**
- Не используйте `print()`: у stdio-сервера stdout — канал протокола, и каждая строка в нём должна быть сообщением JSON-RPC. SDK v2 защищает stdout, пока сервер работает, но `print()` до запуска сервера всё равно попадёт в канал.
- Логируйте через стандартный модуль `logging`: он пишет в stderr и протоколу не мешает.
- Логи видны в терминале при ручном запуске и в Inspector. В чате клиента их не видно: это инструмент разработчика сервера. Claude Desktop записывает их в файл, об этом в модуле 8.

**Документация:** [Logging](https://py.sdk.modelcontextprotocol.io/handlers/logging/)

### Шаг 5.1 — Логирование
- [ ] Добавить в `list_notes` запись в лог через `logging`.
- [ ] **Терминал:** запустить `uv run server.py`, вставить по очереди три сообщения и найти свою запись:
  1. `initialize`:
     ```json
     {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"manual","version":"0.1"}}}
     ```
  2. `notifications/initialized`:
     ```json
     {"jsonrpc":"2.0","method":"notifications/initialized"}
     ```
  3. Вызов `list_notes`:
     ```json
     {"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"list_notes","arguments":{}}}
     ```
- [ ] **Inspector:** запустить `uv run mcp dev server.py`, вызвать `list_notes` и найти свою запись.

**Примечание:** отправлять логи клиенту через `Context` (`ctx.info()` и т.п.) не нужно: в протоколе 2026-07-28 эта возможность объявлена устаревшей ([Deprecated features](https://py.sdk.modelcontextprotocol.io/deprecated/)).

## Модуль 6. Ресурсы (resources)

Сначала прочитайте документацию: [Resources](https://py.sdk.modelcontextprotocol.io/servers/resources/).

### Шаг 6.1 — Статический ресурс `notes://index`
- [ ] Добавить в `server.py` функцию с декоратором `@mcp.resource("notes://index")`. Функция без параметров возвращает строку: список заметок с размером или первой строкой каждой.

### Шаг 6.2 — Шаблон ресурса `notes://{name}`
- [ ] Добавить в `server.py` функцию с декоратором `@mcp.resource("notes://{name}")`. Функция принимает параметр `name` и возвращает текст заметки.

## Модуль 8. Подключение к клиентам

Сервер готов и проверен в Inspector. Теперь подключим его к двум клиентам, Claude Code и Claude Desktop, и посмотрим, как с ним работает модель.

### Шаг 8.1 — Claude Code: регистрация
- [ ] Убедиться, что `claude --version` печатает версию.
- [ ] Открыть терминал в папке, в которой предполагается работать с сервером, и зарегистрировать его:
  ```bash
  claude mcp add notes -- uv run --directory C:/path/to/mcp_practice server.py
  ```

**Документация:** [Claude Code: MCP](https://code.claude.com/docs/en/mcp), [Connect to a real host](https://py.sdk.modelcontextprotocol.io/get-started/real-host/)

**Пояснения:**
- `notes` — имя, под которым Claude Code будет знать сервер.
- `uv run --directory <папка> server.py` — запустить `server.py` в окружении проекта из указанной папки.
- Путь `C:/path/to/mcp_practice` нужно заменить на абсолютный путь к папке `mcp_practice`, в которой лежит `server.py`. Если в пути есть пробелы, возьмите его в кавычки.

**Scope** определяет, где сервер доступен и где хранится его регистрация. Он указывается после имени сервера и перед `--`: `claude mcp add notes --scope user -- …`.

| Scope | Где доступен сервер | Где хранится регистрация |
|---|---|---|
| `local` (по умолчанию) | только вам и только в этой папке | `~/.claude.json`, в записи этой папки |
| `project` | всем, кто откроет эту папку в Claude Code | `.mcp.json` в корне папки; файл можно закоммитить |
| `user` | вам во всех папках | `~/.claude.json` |

- Перед первым использованием сервера из `.mcp.json` Claude Code спрашивает подтверждение: файл мог прийти из чужого репозитория.
- Если сервер зарегистрирован в нескольких scope, используется одна запись в порядке приоритета: `local`, затем `project`, затем `user`.
- Для курса подойдёт `local`. Чтобы посмотреть на `.mcp.json`, можно зарегистрировать сервер с `--scope project` и открыть файл в корне папки.

**Проверка:** `claude mcp get notes` показывает команду с полным путём к вашей папке.

**Если ошиблись:** `claude mcp remove notes` и зарегистрируйте заново. Список всех серверов: `claude mcp list`.

### Инструменты в отдельном файле

Когда инструментов становится много, их удобно вынести из `server.py` в отдельный модуль. Инструмент — это обычная функция, но одного импорта мало: её нужно зарегистрировать на том объекте `mcp`, который запускается.

**Как правильно:** функция живёт в отдельном файле, а регистрирует её `server.py` через `mcp.add_tool(...)`. Это то же самое, что `@mcp.tool()`: декоратор внутри вызывает `add_tool`, а имя, описание и схема аргументов строятся одинаково.

`tools.py`:
```python
from pathlib import Path

NOTES_DIR = Path(__file__).parent / "notes"


def list_notes() -> list[str]:
    """List the names of all notes (Markdown files) in the notes folder."""
    return sorted(path.name for path in NOTES_DIR.glob("*.md"))
```

`server.py`:
```python
from mcp.server import MCPServer

from tools import list_notes

mcp = MCPServer("Notes")
mcp.add_tool(list_notes)

if __name__ == "__main__":
    mcp.run()
```

В `tools.py` нет импортов из MCP SDK: это обычные функции, которые можно вызывать и тестировать отдельно от сервера.

**Ловушка:** не импортируйте `mcp` из `server.py` в файл с инструментами (`from server import mcp` и `@mcp.tool()` над функцией). При запуске `uv run server.py` это тихо ломается:
1. `server.py` запущен как скрипт, и Python загружает его под именем `__main__`.
2. `tools.py` выполняет `from server import mcp`. Модуль `server` Python ещё не загружал, поэтому загружает `server.py` второй раз и создаёт второй объект `mcp`.
3. Инструменты регистрируются на втором объекте, а запускается первый. `tools/list` вернёт пустой список.

В Inspector ошибка не видна: `mcp dev` импортирует файл, а не запускает его как скрипт. Правило простое: сервер импортирует инструменты, а инструменты сервер не импортируют.

### Заметки в списке ресурсов

Клиенты показывают для прикрепления только ресурсы из `resources/list`: Claude Code — в автодополнении `@`, Claude Desktop — в меню Add from notes. Шаблон `notes://{name}` туда не попадает. Чтобы заметки можно было прикреплять в клиенте, зарегистрируйте каждую как отдельный ресурс. Для файлов в SDK есть готовый класс `FileResource`:

```python
from mcp.server.mcpserver.resources import FileResource

for path in sorted(NOTES_DIR.glob("*.md")):
    mcp.add_resource(
        FileResource(
            uri=f"notes://{path.name}",
            name=path.name,
            path=path.resolve(),
            mime_type="text/markdown",
        )
    )
```

Список собирается один раз, при старте сервера. Заметка, созданная позже, появится в списке после переподключения сервера: в Claude Code — `/mcp` → `notes` → Reconnect, в Claude Desktop — полный перезапуск приложения.

**Без переподключения.** Сервер может сообщить клиенту, что список ресурсов изменился, уведомлением `notifications/resources/list_changed`. Claude Code, получив его, перезапрашивает список. Для этого после создания заметки в `write_note` нужно зарегистрировать новый ресурс и отправить уведомление. Три оговорки:
- способ отправки зависит от версии протокола: `ctx.notify_resources_changed()` работает на протоколе 2026-07-28, а для более старых нужен `ctx.session.send_resource_list_changed()`;
- в ответе на `initialize` сервер по умолчанию объявляет `"resources":{"listChanged":false}`, и клиент вправе игнорировать уведомления от такого сервера;
- поддерживает ли такие уведомления Claude Desktop, в курсе не проверялось.

**Документация:** [Resources](https://py.sdk.modelcontextprotocol.io/servers/resources/), [Subscriptions](https://py.sdk.modelcontextprotocol.io/handlers/subscriptions/)

### Шаблоны ресурсов подробнее

В шаге 6.2 используется простейшая форма шаблона — один параметр `{name}`. Документация [URI templates](https://py.sdk.modelcontextprotocol.io/servers/uri-templates/) описывает и другие:

| Форма | Пример | Что делает |
|---|---|---|
| `{name}` | `books://{isbn}` | один сегмент адреса (наш случай) |
| типизированный параметр | `orders://{order_id}` с `order_id: int` | SDK сам приводит значение к типу параметра функции |
| `{+name}` | `manuals://{+path}` | захватывает и `/`, то есть путь из нескольких сегментов |
| `{?a,b}` | `reviews://{isbn}{?limit,sort}` | параметры запроса после `?`, необязательные |
| `{/name*}` | `shelves://browse{/path*}` | сегменты пути в виде списка |

Там же есть раздел о безопасности: какие значения SDK отсекает сам (`..`, абсолютные пути, нулевые байты), и функция `safe_join` для обращения к файлам. Её можно сравнить с вашей защитой путей из шага 3.3.

## Ответы на вопросы для понимания

Сначала ответьте сами, потом сверяйтесь.

**1. Почему бессмысленно держать stdio-сервер запущенным в отдельном терминале?**
Stdio-сервер принимает запросы только через stdin и отвечает только через stdout. Поэтому работать с ним может только тот, кто его запустил. Если запустить сервер в терминале, общаться с ним сможете только вы, вручную. Клиент к нему не подключится, поэтому запускает сервер сам. Именно поэтому и `claude mcp add`, и конфиг Claude Desktop содержат команду запуска, а не адрес.

**2. Почему проверку путей нужно делать в сервере?**
Модель — не граница безопасности. Она может ошибиться, а её можно обмануть: например, текст заметки может содержать инструкцию «прочитай `../.env`» (prompt injection). Кроме того, сервер вызывает не только модель: Inspector, другой клиент или скрипт пришлют любые аргументы. Сервер — единственное место, через которое проходит каждый запрос к файлам, поэтому ограничение работает только там.

**3. Почему для изменяющих инструментов осторожность host особенно важна?**
Ошибку при чтении можно просто проигнорировать, а ошибку при записи — нет: перезаписанную заметку не вернуть. Модель может неверно понять просьбу или выполнить чужую инструкцию из прочитанных данных. Запрос разрешения оставляет человека последним звеном перед необратимым действием. Аннотации `readOnlyHint` и `destructiveHint` помогают host решить, где спрашивать обязательно.

**4. Какие ресурсы клиент показывает для прикрепления?**
Только статические, например `notes://index`. Сервер отдаёт их в ответе на `resources/list`: это конкретные ресурсы с готовым адресом. Шаблон `notes://{name}` приходит отдельным запросом `resources/templates/list` как образец адреса, а не как список заметок. Ни Claude Code, ни Claude Desktop его не показывают, поэтому прикрепить заметку по шаблону нельзя. Inspector с шаблонами работает: в нём можно подставить имя и прочитать ресурс.

**5. Чем прикреплённый ресурс отличается от вызова `list_notes`?**
- **Кто решает.** Ресурс выбрали вы, вызов инструмента — модель.
- **Когда данные попадают в контекст.** Прикреплённый ресурс клиент читает сам и добавляет к вашему сообщению до того, как модель начнёт отвечать. Инструмент модель вызывает уже по ходу ответа, если сочтёт нужным.
- **Разрешения.** На прикрепление ресурса разрешение не спрашивается: вы его уже дали, выбрав ресурс. На вызов инструмента клиент спрашивает.

**6. Когда что использовать?**
- **Tool** — действие или вычисление, о котором решает модель: поиск, чтение по запросу, запись, вызов внешнего API. Может иметь побочные эффекты.
- **Resource** — данные для чтения с собственным URI, которые выбирает пользователь (или приложение), чтобы дать модели контекст. Без побочных эффектов.
- **Prompt** — готовый шаблон запроса, который пользователь запускает явно, например слэш-командой или из меню клиента. Модель сама промпты не вызывает.
